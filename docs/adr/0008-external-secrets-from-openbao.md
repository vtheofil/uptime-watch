# 0008. Secrets from outside: OpenBao next to the cluster, External Secrets inside

- Status: Accepted
- Date: 2026-11-20

## Context

Most secrets are generated by `bootstrap.sh` (the Postgres password,
`ADMIN_TOKEN`) and may die with the cluster, like the database. The Discord
webhook URL is different: it comes from outside and was typed in again after
every rebuild (`make kind-discord-secret`). It must not be in git, and it
should come back by itself when the cluster is rebuilt.

## Decision

- **OpenBao** (the open-source fork of HashiCorp Vault) holds such secrets. It
  runs **outside the kind cluster**, as a Docker container on kind's network,
  so its data survives `make kind-down`. Raft storage in a Docker volume, one
  unseal key, plain HTTP on 127.0.0.1 (`deploy/openbao/`).
- **External Secrets Operator** (ESO) runs inside the cluster (Argo CD, wave
  -3). A `ClusterSecretStore` points at OpenBao; an `ExternalSecret` copies
  `secret/uptime-watch/discord` into `monitoring/alertmanager-discord` and
  refreshes it every 15 minutes (`deploy/secrets/`, wave 3).
- ESO logs in with a **token limited to reading `secret/uptime-watch/*`**,
  which `bootstrap.sh` creates and stores as `external-secrets/openbao-token`:
  the one secret still put into a new cluster by hand ("secret zero").
- The secrets app is the **last wave**: if OpenBao is down or the secret is
  missing, it shows Degraded but blocks nothing. Alertmanager runs without the
  webhook and picks it up when it appears (it reads the file on every send).

## Consequences

- A rebuild is `kind-up`, `openbao-up`, `kind-argocd`; the webhook returns by
  itself. Changing the webhook is one write to OpenBao.
- OpenBao becomes something to run and to unseal after each restart
  (`make openbao-up`), and its init file (unseal key and root token,
  `~/.config/uptime-watch/openbao-init.json`) must be kept safe: lose it and
  the secrets cannot be opened.
- The ESO token is periodic and lasts 32 days without renewal; rebuilds make a
  new one. OpenBao's Kubernetes auth (ESO proves itself with its service
  account, no static token) is the next step.
- Laptop shortcuts, wrong for production: a single unseal key in a file, the
  root token kept, no TLS.
- `make kind-discord-secret` remains for clusters without OpenBao; using both
  conflicts, because the ExternalSecret owns that Secret.

## Alternatives considered

- **Sealed Secrets**: encrypted secrets in git, decrypted by a controller.
  Simple, but the decryption key lives in the cluster and must itself be
  backed up and restored on every rebuild.
- **SOPS with age keys**: encrypted files in git, decrypted by Argo CD with a
  plugin; again a key to bring into each new cluster.
- **OpenBao inside the cluster**: its data would die with the cluster, the
  problem we started from.
- **A cloud secret manager**: the usual choice in a cloud, not available on a
  laptop; ESO would talk to it the same way.
